# BREAKOUT.md - institutional breakout entry detector spec

This file is the authoritative build spec for a cross-asset breakout entry
detector. It is deliberately scoped to entry detection only. It does not manage
portfolio construction, exits after entry, capital allocation, or full order
execution. It does, however, produce the entry signal metadata needed by later
modules: direction, trigger timestamp, actionable entry timestamp, quality
score, invalidation level, stop-distance estimate, execution urgency, and
evidence decomposition. The narrow outward composition surface (what SYSTEM and
EXECUTION may read) is pinned in Section 7 and Invariants K-M.

Target quality level:
- Research architecture: 9/10 or better.
- Signal sophistication: 9/10 or better.
- Detector production readiness: 9/10 or better for the detector layer only.

The thesis is:

1. A good breakout entry is not just a new high or low. It is a transition from
   compression or balanced auction into directional expansion.
2. The best entries are convex: small invalidation distance, asymmetric upside
   continuation potential, and low immediate reversion risk.
3. The detector must be online-safe. If a signal fires at bar t, every number
   used by that signal must be computable at or before bar t. Future bars are
   allowed only inside validation labels and reports.
4. The same code must run on commodity futures, metals, US equities, and crypto.
   Asset-specific behavior comes from data adapters, metadata, costs, calendars,
   and fitted distributional profiles, not from forking detector logic.

This spec is designed to be fed directly to a coding agent. Build to the
contracts and invariants below. Ask before breaking any invariant.

---

## 0. What "done" means

A first institutional-grade detector build is done when all of these are true:

1. The full detector runs end-to-end on synthetic 1-minute data generated by the
   repo. No external data is required to run unit tests.
2. The full detector runs in both batch replay mode and streaming one-bar update
   mode, and the emitted signals are bitwise or tolerance-equal.
3. `validate/walkforward.py` scores entry quality from the actionable entry bar,
   not from the signal bar unless they are the same.
4. `validate/baselines.py` produces the same report shape under identical
   splits, costs, entry timestamps, and embargo rules.
5. `validate/labels.py` creates future labels only for evaluation: MFE, MAE,
   first-touch of stop/profit barriers, time-to-continuation, and false-breakout
   rate. These labels are structurally unreachable from the online detector.
6. `tune/autotune.py` can add a new symbol, fit instrument-specific profiles,
   calibrate empirical null thresholds, run validation, and output one of:
   `approved`, `shadow`, or `rejected`.
7. All invariants in Section 5 have explicit tests.

Do not add a learned black-box classifier in v1. The core should be statistical,
auditable, monotone where possible, and decomposable. If a future learned model
is added, it must be a separate challenger path and must clear the same
purged/embargoed validation, ablation, and multiple-test controls.

Stack: Python 3.11+, numpy, scipy, pandas, pytest. Numba is allowed only for
speed-sensitive rolling computations after correctness tests exist. No heavy ML
frameworks in v1.

Algorithmic cost (load-bearing for the 87-instrument, 2-core ARM,
seconds-latency retail target): the rolling max/min barriers (Donchian) and
rolling quantiles must be **amortized O(1) per bar**, not O(W) recomputation:

- Rolling max/min: monotonic deque (each bar pushed and popped at most once).
- Rolling quantiles / percentiles (range-width and compression distributions):
  a streaming order-statistic structure — P-square, or a bounded fixed-bin
  histogram — giving O(1) amortized update with bounded memory.

Therefore the full online update is O(1) per instrument per bar (the whole
87-instrument 1-minute tick is O(87) work), and the batch replay pass is O(n)
in bars. No barrier or quantile may be implemented as an O(W) windowed
recompute on the hot path. See Invariant E and `online/state.py` below: the
deque/histogram state is part of the serializable snapshot so batch and live
produce identical numbers.

## 2. Parameter governance

Every parameter belongs to exactly one bucket. Misfiling a parameter is a
research bug, because it can turn auto-tuning into hidden overfit.

### TEAL - fitted from each instrument's own past data

TEAL values are free to differ by instrument, but they must be fitted at runtime
inside a fit object. They are not hand-set in `InstrumentSpec`.

Examples:
- Intraday volatility seasonality.
- Liquidity/volume/spread seasonality.
- Rolling volatility scale.
- Student-t tail parameter or robust tail index.
- Range width distribution.
- Compression percentile distribution.
- Empirical null distribution of detector statistics conditional on regime
  bucket.
- Symbol-specific missing-data and stale-bar profile.

TEAL fitting rule: a value applied at bar t may use only data available before
or at t. For daily/session profiles applied inside session S, use only sessions
strictly before S unless the method is explicitly online-recursive.

### AMBER - supplied instrument metadata

AMBER values differ by instrument for real market-structure reasons. They are
supplied by the caller, metadata registry, or data adapter. They are not
optimized by the detector.

Examples:
- Asset class and venue.
- Session calendar, RTH/ETH policy, 24/7 policy.
- Tick size, lot size, price multiplier.
- Futures roll/stitching rule and contract expiry metadata.
- Corporate action adjustment source for equities.
- Fee schedule, estimated spread, slippage model for validation.
- OFI/trade/quote data source availability.
- Funding-rate availability for crypto perps.
- Shortability/halts/auction flags for equities.

### RED - shared modelling choices

RED values are modelling policies. They live in `DetectorDefaults`. They are
shared across instruments unless a class-level override is validated.

Examples:
- Target false-alert policy: ARL0, FDR, or expected alerts per session.
- Candidate breakout barrier family (see barrier-family policy below).
- Breakout-confirmation cross magnitude `k` (penetration in causal-sigma/ATR
  units, Invariant J). Single shared scalar; BLUE-searchable, never per-symbol.
- Evidence-combination rule.
- Purge/embargo policy.
- Evaluation horizons.
- Stop/invalidation policy family.
- Minimum out-of-sample evidence needed for promotion.
- Allowed baselines and ablations.

RED values must never appear in `InstrumentSpec`.

#### Barrier-family policy (RED, per asset-class; not an owner whim)

The barrier family that defines `upper_barrier`/`lower_barrier` (Donchian,
robust rolling quantile, opening-range, anchored-session-range) is a RED
*modelling policy chosen per asset-class*, NOT a free per-instrument choice and
NOT "owner to decide." It materially changes the barrier and the false-breakout
profile, so it is governed:

- 24/7 instruments (crypto, calendars with no session boundary): the family is
  **rolling Donchian of window W** by default. The UTC day/week boundary used by
  any anchored variant comes from `data/calendar.py`'s 24/7 segmentation
  (Section 3, crypto), never an ad-hoc midnight.
- Instruments whose `calendar_id` declares sessions (futures, metals, equities):
  the **session-anchored opening-range** variant is permitted, with the session
  boundary taken from AMBER calendar metadata.
- The opening-range / anchored-session variant is DISABLED for any instrument
  whose `calendar_id` has no session boundary, so the same code path is
  deterministic across the universe (no silent fallback to an undefined anchor).

The chosen family is recorded in `ResolvedConfig` and is subject to the same
OOS promotion gate as `W` and `k` (Section 10).

### BLUE - controlled auto-tuning candidates

BLUE values are finite candidate sets searched by `tune/autotune.py`. BLUE is
not "optimize until it looks good." It is a governed search over a small,
predeclared space.

Examples:
- Candidate lookback windows: `[20, 40, 80, 160]`.
- Candidate ARL0 targets: `[250, 500, 1000, 2000]`.
- Candidate compression windows: `[30, 60, 120]`.
- Candidate evidence-combiner presets: `strict`, `balanced`, `early`.
- Candidate validation horizons: `[15, 30, 60, 120]` bars.

BLUE search can select:
- One global default.
- One asset-class override.
- One liquidity-bucket override inside an asset class.

BLUE search must not select arbitrary per-symbol RED values. A new symbol can
auto-fit TEAL values and inherit approved RED/BLUE defaults. Symbol-specific
promotion is allowed only as a registry status (`approved`, `shadow`,
`rejected`), not as unconstrained parameter optimization.

## 3. Asset-class customization

The detector logic remains common. Customization enters through AMBER metadata,
TEAL fitted profiles, optional feature availability, and class-level BLUE
overrides only after validation.

### Commodity futures

Required AMBER:
- Exchange calendar and session segmentation.
- Contract multiplier, tick size, limit rules if available.
- Roll rule: front month, volume/open-interest switch, or constant maturity.
- Expiry and holiday metadata.

Required TEAL:
- Session-open/gap profile.
- Roll-window liquidity profile.
- Intraday volume and volatility seasonality.
- Empirical null by session segment.

Validation notes:
- Report performance separately for roll windows and normal sessions.
- Report event-window behavior for inventory reports and major scheduled data
  where timestamps are supplied.
- Verify that stitched contracts do not fabricate breakouts near rolls.

### Metals

Metals are not one homogeneous group.

Required AMBER:
- Venue and contract metadata for COMEX/LME/spot/perp source.
- Session and fixing/settlement windows when relevant.
- Roll rules for futures.

Required TEAL:
- Separate profiles for precious metals and industrial metals if both are used.
- Gap/jump diagnostics around macro windows.
- Liquidity profile by venue/session.

Optional context:
- USD/rates context for precious metals.
- Growth/risk/copper complex context for industrial metals.

Validation notes:
- Do not assume gold, silver, copper, and aluminum share the same null.
- Class override must be at least `precious_metals` vs `industrial_metals` if
  validation proves one shared setting leaves robust edge on the table.

### US equities

Required AMBER:
- Corporate-action adjustment source.
- RTH/ETH policy.
- Halt and auction flags if available.
- Tick size, venue, fee/spread assumptions.
- Universe membership point-in-time if evaluating many symbols.

Required TEAL:
- Opening/closing auction volatility profile.
- Intraday volume U-shape and spread profile.
- Earnings/event flags if supplied.
- Liquidity-bucket null distributions.

Validation notes:
- Report small/mid/large/liquid buckets separately.
- Separate single-name equities from index ETFs.
- Exclude or separately report earnings windows, halts, and extreme gap opens.
- Use survivorship-free data for universe tests.

### Crypto

Required AMBER:
- Exchange/venue and symbol mapping.
- Spot vs perpetual instrument type.
- Maker/taker fee schedule.
- Funding-rate availability for perps.
- 24/7 calendar with UTC day/week segmentation.
- Outage/stale-data flags if available.

Required TEAL:
- Day-of-week and hour-of-day seasonality.
- Weekend liquidity profile.
- Exchange-specific spread/slippage profile.
- Empirical null by liquidity and volatility regime.

Optional context:
- Funding surprise, open interest, liquidations, basis, and cross-exchange
  premium if available.

Barrier anchoring (RED, see Section 2 barrier-family policy):
- The 24/7 sub-universe uses the **rolling Donchian of window W** family by
  default. The choice between rolling-Donchian and a session-anchored variant is
  NOT left undefined: crypto `calendar_id` has no session boundary, so the
  opening-range / session-anchored variant is DISABLED for it, and any UTC
  day/week anchor (if a future anchored variant is enabled) must come from
  `data/calendar.py`'s 24/7 UTC segmentation. This makes the barrier
  deterministic across the universe rather than depending on an implicit
  midnight convention.

Validation notes:
- Centralized order-book signals are exchange-specific.
- Fragmentation matters: OFI from one venue is not "the crypto market."
- Report weekday/weekend and high/low funding regimes separately.

### Cross-asset context

Cross-asset features are optional evidence channels, never hard requirements.
They must be current or lagged at the signal timestamp.

Allowed examples:
- Equity index or sector ETF confirmation for US equities.
- USD/rates context for metals.
- Oil/gas complex context for energy commodities.
- BTC/ETH market regime for alt crypto.
- Broad risk-on/risk-off proxy.

Cross-asset context must be evaluated by ablation. If it does not improve
out-of-sample entry quality net of costs, it remains disabled.

## 5. Architectural invariants

These are structural rules, not style preferences.

### Invariant A - only `detect/combine.py` emits `EntrySignal`

Feature modules and detector-stat modules return arrays or `EvidenceFrame`.
They never emit final entries. Only `SignalAssembler.fire()` in
`detect/combine.py` can create an `EntrySignal`.

### Invariant B - no future data in online signal generation

For a signal with `signal_idx=t`, every field in the signal must be computable
from data up to and including t. If the entry is delayed to t+1, no t+1 price or
volume may influence the decision to fire at t.

### Invariant C - future labels are evaluation-only

`EntryLabel`, MFE, MAE, first-touch labels, horizon returns, and false-breakout
labels live only under `validate/`. They must not be imported by `detect/`,
`features/`, `standardize/`, `online/`, or `pipeline.py`.

### Invariant D - RED and BLUE are unreachable from `InstrumentSpec`

`InstrumentSpec` contains AMBER metadata only. No ARL0, threshold, horizon,
lookback, score weight, stop policy, or candidate grid may be stored there.

### Invariant E - batch/live parity

Running `PipelineOrchestrator.run_batch(bars)` must produce the same signals as
feeding the same bars one at a time through `PipelineOrchestrator.update(bar)`,
after warm-up handling. This must be tested for every core module. The O(1)
streaming structures from Section 1 (monotonic deque for rolling extrema,
P-square/histogram for quantiles) are the live update path; batch replay must
yield bit/tolerance-identical signals, which requires the full deque/histogram
state to live in the `online/state.py` snapshot (see below).

### Invariant F - baselines share identical evaluation contracts

Every baseline uses the same bars, costs, entry timestamp convention, split
objects, embargo, horizons, and label function as the main detector.

### Invariant G - confirmation delay moves the entry

If any optional confirmation requires waiting k bars, then `entry_idx` must move
forward by k bars. A detector may not wait for future evidence and then score as
if it entered at the original signal bar.

### Invariant H - scores are decomposable

Every `EntrySignal` must include component evidence values and reason codes.
If a signal cannot explain why it fired, it is invalid.

### Invariant I - barriers are strictly pre-bar

This is the single most common breakout-detector correctness defect, and it is
distinct from the future-needle test (Invariant B / Section 12.4), which only
checks bars *after* t. The defect here is *self-reference at t*.

`upper_barrier[t]` and `lower_barrier[t]` in `BreakoutGeometry` must be
functions of bars `[.. t-1]` only. They must NOT contain bar t's own
high/low/close. The cross test in `detect/candidates.py` compares bar t's price
against a level that does not contain bar t.

Why this is load-bearing: a Donchian level computed *inclusive* of t, i.e.
`upper_barrier[t] = rolling_max(h[t-W+1 .. t])`, is unbreakable by construction
because `h[t]` is already inside the max. `c[t] > upper_barrier[t]` can then
only fire on a degenerate tie (`c[t] == h[t]` and that is the window max), so a
naive implementer either never fires or fires on a measure-zero edge. The
correct, fireable definition is strictly causal:

```text
upper_barrier[t] = rolling_max(h[t-W .. t-1])   # window ends at t-1
lower_barrier[t] = rolling_min(l[t-W .. t-1])
```

Equivalently: compute the inclusive rolling extremum, then shift forward by one
bar (`barrier[t] = inclusive_extremum[t-1]`). The opening-range and
anchored-session variants obey the same rule: the range that bar t breaks is the
range *as declared complete strictly before t* (see the Section 2 barrier-family
policy and the Section 3 crypto anchoring policy above for 24/7 anchoring).

This invariant binds every barrier family in `range_geometry.py`. Its test
(Section 15: "barrier-is-strictly-pre-bar test") asserts that
`upper_barrier[t]` equals the rolling extremum over `[t-W .. t-1]` and that
raising bar t's own high does not raise the level it must break.

### Invariant J - cross magnitude is vol-normalized, not raw price

The candidate cross in `detect/candidates.py` must not be a raw-price
comparison. A 1-tick poke past a Donchian high and a 1-sigma thrust past it are
not the same event, and treating them identically makes the trigger
non-comparable across the 87-instrument universe (a tick is a different fraction
of sigma on BTC than on a 5-tick equity). Penetration past the barrier must be
expressed in causal-sigma (preferred) or ATR units:

```text
fire long candidate at t  iff  c[t] - upper_barrier[t] >= k * sigma_t
fire short candidate at t iff  lower_barrier[t] - c[t] >= k * sigma_t
```

where `sigma_t` is the past-only standardizing scale from `StdSeries.sigma[t]`
(itself `F_{t-1}`-measurable per Section 12.2) and `k` is a single
RED-default / BLUE-searched scalar (the same `k` runs on crypto and equities).
`k` and the `windows` lookback are governed RED/BLUE and OOS-validated
(Section 10 promotion gate); they are NEVER fit per symbol on PnL. See the
"same-k-cross test" in Section 15.

### Invariant K - score-magnitude firewall to downstream composition

BREAKOUT owns `quality_score`, `threshold`, and `evidence` for its OWN gating
and validation only. Downstream composition (SYSTEM/REGIME/LEVERAGE) consumes
this module through a deliberately narrow surface. The only fields downstream
may branch on are:

- `direction` (the side), and
- the boolean `status == "entry"` (qualified or not).

Price fields (`invalidation`, `stop_distance`, `entry_ref_price`,
`barrier_price`, `entry_idx`) are consumed as *levels*, not as ranking inputs.
`quality_score` magnitude is NOT a downstream ranking input. This matches
SYSTEM.md Invariant CB: multiplying every breakout `quality_score` by a positive
constant must not change any `SystemDecision`. The score is for BREAKOUT's
internal accept/reject and for its own diagnostics; it is opaque to composition.
See the "score-scale-invariance contract test" in Section 15.

### Invariant L - cross-sectional selection bias is controlled at promotion

Scanning one fixed detector across the 87-instrument universe and surfacing the
ones that look good manufactures cross-sectional false positives. SYSTEM.md's
DSR (its Section 7.1) deflates the JOINT BLUE-grid multiplicity (`N_sys` over
composed configs) within a symbol; it does NOT see the cross-sectional
instrument scan. Therefore per-symbol promotion in `tune/promotion.py` MUST
control the cross-sectional FDR/FWER over the universe scanned (Section 10
promotion gate). The universe-scan trial count is recorded in the registry
artifact (Section 11) so it can feed SYSTEM's persistent ledger (SYSTEM
Invariant SG). This is the cross-symbol analogue of the existing "no single
symbol may explain most of the result" fold rule.

### Invariant M - regime boundary: local conditioning bucket, not global state

BREAKOUT's `empirical_null` vol/liquidity regime *bucketing* (Section 7,
`detect/empirical_null.py`; the `vol_bucket` / `liq_bucket` integers in
`StdSeries`) looks like it re-derives the regime state REGIME.md already emits
(its continuous `g(s_t)` and discrete state `s_t`). It deliberately does NOT,
and the boundary is pinned here to satisfy "consume not duplicate":

- BREAKOUT keeps an INDEPENDENT, instrument-local, past-only bucket whose ONLY
  job is conditional null calibration (which empirical-null distribution to draw
  a p-value/e-value from). It is a within-instrument standardization device, it
  is `F_{t-1}`-measurable, and it is fit from that instrument's own history. It
  must stay local because the null must be conditioned on the *same instrument's*
  recent vol/liquidity, not a cross-sectional risk regime.
- BREAKOUT does NOT consume, reproduce, or gate on REGIME's global `g(s_t)`.
  The global risk multiplier is a *downstream ceiling*: it is applied by
  LEVERAGE (sizing) and/or SYSTEM (gating) to BREAKOUT's output, never folded
  into `quality_score`. This keeps composition `min()`-not-product and keeps the
  detector decomposable.

So the two "regimes" are different objects: REGIME emits a *global, cross-asset
risk state* for sizing/gating; BREAKOUT holds a *local null-calibration bucket*
for p-value validity. Neither subsumes the other, and `g(s_t)` enters only at
the downstream composition slot.

## 6. Detector concept

The detector is built around six independent questions:

1. Did price cross a meaningful barrier?
2. Was the market compressed or balanced before the cross?
3. Is there evidence of a regime change in mean, variance, or both?
4. Is the move directional rather than a one-bar spike or liquidity sweep?
5. Is the invalidation distance tight relative to expected expansion?
6. Does optional flow/context reduce false-breakout risk out of sample?

The system should prefer fewer, higher-quality entries over many weak triggers.
It is a breakout entry detector, not a generic trend-following indicator.

#### Public composition adapter (the contract SYSTEM wraps)

`SignalAssembler.fire(...) -> list[EntrySignal]` is the rich internal emitter.

```python

    propose() returns at most one currently-actionable EntrySignal for the
    instrument (the highest-quality un-deduped 'entry' at the latest bar), or
    None when nothing qualifies. SYSTEM's breakout_adapter.py adapts the
    returned EntrySignal to SYSTEM's Signal type, reading ONLY direction,
```

- SYSTEM branches only on `direction` and `status == "entry"` (Invariant K).

## 8. Evidence combination

The final quality score must be decomposable and monotone in good evidence.
Do not train arbitrary feature weights in v1.

Recommended v1 approach:

1. Convert each evidence channel into calibrated evidence:
   - `glr_e`
   - `bocpd_e`
   - `range_e`
   - `compression_e`
   - `flow_e`
   - `jump_e`
   - `context_e`
2. Penalize immediate false-break risk:
   - wick rejection
   - poor close location
   - too-wide stop distance
   - too-narrow/noisy range
   - stale or invalid bars
3. Combine with a fixed preset:

```text
quality_score =
    w_glr * glr_e
  + w_bocpd * bocpd_e
  + w_range * range_e
  + w_compression * compression_e
  + w_flow * flow_e
  + w_jump * jump_e
  + w_context * context_e
  - w_false * false_break_risk
```

Weights are RED or BLUE preset values, never fit freely per symbol.

Allowed presets:
- `strict`: fewer entries, requires stronger regime-change evidence.
- `balanced`: default.
- `early`: earlier entries, higher false-break risk, must be validated.

Optional channels default to zero and must be enabled only if ablation proves
benefit.

## 9. Stop-aware entry quality

The detector must output an invalidation level and stop-distance estimate, even
though full stop management belongs to a later trading module.

Purpose:
- Prefer entries where the breakout thesis is invalidated quickly if wrong.
- Measure convexity in validation as MFE_R versus MAE_R.
- Avoid breakouts whose stop distance is so wide that trend convexity is gone.

Rules:

1. `invalidation` must be computable at signal time.
2. `stop_distance` must be positive and above a minimum tick/spread floor.
3. Entries with stop distance below the noise floor are rejected.
4. Entries with stop distance above the configured max R budget are rejected.
5. The detector does not decide exit logic after entry. It only supplies the
   invalidation reference needed by validation and later trading modules.

Validation labels must report:
- `hit_plus_1r_before_stop`
- `hit_plus_2r_before_stop`
- `hit_stop_first`
- `median_mfe_r`
- `median_mae_r`
- `convexity_ratio`
- `false_breakout_rate`

This is the main bridge between breakout detection and the later goal of trend
convexity with tight stop loss.

## 10. Validation metrics

Accuracy against synthetic changepoints is not enough. The detector must clear
entry-quality metrics that correspond to tradeable breakouts.

Required headline metrics:
- Signals per day/session.
- Net forward return in bps from `entry_idx`.
- Hit +1R before stop.
- Hit +2R before stop.
- Stop hit first.
- Median MFE_R.
- Median MAE_R.
- Convexity ratio.
- False-breakout rate.
- Quality-score decile monotonicity.
- Time-to-continuation distribution.
- Performance by volatility bucket.
- Performance by liquidity bucket.
- Performance by session segment.
- Performance by asset class.
- Performance versus each baseline.

Required statistical controls:
- Confidence intervals by fold/path.
- Bootstrap or block-bootstrap confidence intervals for signal outcomes.
- Multiple-test adjustment or deflated/probabilistic Sharpe-style correction
  for BLUE search (the WITHIN-symbol parameter-grid multiplicity).
- Cross-sectional multiple-test control over the universe scan (the BETWEEN-
  symbol multiplicity). These are two distinct multiplicities and BOTH must be
  deflated; see the two gates below.
- Random matched-frequency trigger baseline.
- Ablation table for every evidence channel.

Promotion gates:
- Main detector beats Donchian, ATR/Keltner, CUSUM, and random matched-frequency
  baselines on median out-of-sample convexity ratio and false-breakout rate.
- BLUE-selection gate (Invariant J/L follow-on): the BLUE-selected
  `(lookback window W, cross-multiple k, ARL0)` must beat the parameter-free
  Donchian and ATR baselines on BOTH OOS median convexity AND false-breakout
  rate, at the per-instrument level. The significance of that improvement is
  computed under a deflation that counts BOTH the BLUE grid multiplicity AND the
  universe-scan trial count (no crediting a window/k that only wins because many
  configs and many symbols were tried). An improvement that does not survive the
  joint deflation does not promote.
- Cross-sectional selection-bias gate (Invariant L): `tune/promotion.py` must
  control the cross-sectional FDR/FWER over the instruments evaluated in the
  onboarding batch — e.g. Benjamini-Hochberg across the universe, or a
  per-symbol DSR whose `N` is tied to the number of instruments scanned. A
  symbol whose apparent edge does not survive this correction is `shadow`, not
  `approved`. The universe-scan trial count used here is the same one written to
  the registry (Section 11) and fed to SYSTEM's persistent ledger.
- Quality-score top decile must outperform lower deciles.
- No single fold or single symbol may explain most of the result. Symmetrically
  (cross-symbol selection bias): the universe-level result must not be carried by
  a handful of instruments — report and gate on the distribution across symbols,
  not just the pooled mean.
- Costs must not flip the result negative in realistic spread/slippage settings.
- Batch/live parity test passes.
- Leakage tests pass.

## 11. Auto-tuning and symbol onboarding

When a symbol is added, the system should run itself automatically in this
sequence:

1. Validate data schema and market metadata.
2. Apply calendar/session policy.
3. Fit TEAL profiles:
   - volatility seasonality
   - liquidity seasonality
   - tail parameter
   - range distributions
   - compression distributions
   - empirical null buckets
4. Inherit approved defaults for the symbol's asset class and liquidity bucket.
5. Run walk-forward validation and sampled CPCV if enough data exists.
6. Run baseline suite and ablations.
7. Emit a `PromotionDecision`.

Promotion statuses:


Rules:
- Insufficient data means `shadow`, not forced approval.

  persistent multiplicity ledger (SYSTEM Invariant SG). Without it, a 9.x
  detector silently ships a universe of luck.

## 12. Lookahead surfaces that must be sealed

Human review and explicit tests are required for these:

1. Seasonal profiles:
   - No full-sample intraday means.
   - No future quantiles.
   - Session S can use sessions before S only unless online-recursive.

2. Volatility and tail fitting:
   - No full-sample sigma.
   - `sigma[t]` is one-step-ahead PREDICTIVE: formed from `[..t-1]` only
     (F_{t-1}-measurable, excluding the contemporaneous `r[t]`); `x[t]=r[t]/sigma[t]`
     has numerator F_t, denominator F_{t-1} (seals the surface Invariant J relies on).
   - No full-sample Student-t tail fit for a fold.
   - No global winsorization thresholds estimated from all data.

3. Empirical null calibration:
   - Calibration for test fold uses training data only.
   - Online thresholds at t use observations available before or at t only.
   - Regime bucket boundaries must be fold-local or online-recursive.

4. Candidate and barrier geometry:
   - Rolling highs/lows and quantiles must exclude future bars.
   - Strictly-pre-bar (Invariant I): the barrier bar t must break excludes bar
     t's OWN high/low/close. `upper_barrier[t] = rolling_max(h[t-W .. t-1])`,
     window ends at t-1. An inclusive max contains `h[t]` and is unbreakable.
     This is distinct from the future-needle test (which only checks bars after
     t); it is the self-reference defect at t and has its own test.
   - Opening range cannot use bars after the range is declared complete.

5. Entry timestamp:
   - If signal is known after bar close, entry begins at next actionable bar.
   - No scoring from a price unavailable at the signal timestamp.

6. Validation labels:
   - Labels live only under `validate/`.
   - No module outside `validate/` imports labels or label-derived fields.

7. Cross-asset context:
   - Context bars must be timestamp-aligned.
   - No asset may use a later-closing market's future close.

8. Tuning:
   - Test folds cannot influence selected parameters.
   - Candidate trial count must be recorded for multiple-test correction.

Leakage tests must include:
- Future-needle test: changing future bars after t does not change signals at t.
- Batch/live parity test.
- Fold-isolation test: refitting without test fold gives same test-time
  features as strict fold replay.
- Label-firewall test: importing `validate.labels` from detector modules fails.

Do not skip validation modules. For this detector, validation is part of the

## 15. Minimum tests

Required test groups:

- Data schema tests for malformed OHLCV, duplicate timestamps, missing bars,
  stale bars, and invalid sessions.
- Past-only seasonal profile tests.
- Past-only volatility and tail-fit tests.
- Range geometry tests for long and short barriers.
- Barrier-is-strictly-pre-bar test (Invariant I): assert `upper_barrier[t]`
  equals the rolling extremum over `[t-W .. t-1]`; assert that raising bar t's
  own high does NOT raise the level it must break; assert an inclusive-max
  implementation is rejected (a true compression-to-expansion breakout fires
  under the strict barrier but a self-referential inclusive barrier never fires).
- Same-k-cross test (Invariant J): a 1-tick poke past the barrier does NOT
  produce a candidate while a `>= k * sigma_t` thrust does; the SAME `k` runs on
  a crypto fixture and an equity fixture (no per-symbol k); a per-symbol PnL fit
  of `k` is structurally impossible (k is RED/BLUE, unreachable from
  `InstrumentSpec`).
- Invalidation and stop-distance floor/ceiling tests.
- Candidate generation tests.
- GLR and BOCPD no-decision tests.
- Empirical null fold-isolation tests.
- Evidence decomposition tests.
- Signal assembler only-emitter test.
- Dedupe/cooldown tests.
- Label firewall test.
- Entry timestamp convention tests.
- Baseline identical-contract tests.
- Future-needle leakage tests.
- Batch/live parity tests (including snapshot/restore of the deque/histogram
  streaming state, Invariant E).
- Score-scale-invariance contract test (Invariant K): scaling every breakout
  `quality_score` (and `threshold` together) by a positive constant must not
  change the set of emitted `status == "entry"` signals nor their `direction`,
  and the downstream-facing fields (direction, status, urgency, price levels)
  must be byte-identical. A companion test asserts the public adapter
  `BreakoutModule.propose()` exposes only those fields' values to a mock SYSTEM
  adapter.
- Urgency-field test: every emitted `EntrySignal` carries `urgency == "urgent"`
  (breakout entries are adversarial per EXECUTION) and the field is non-null.
- Cross-sectional selection-bias test (Invariant L): given a universe of pure-
  noise instruments, the promotion gate approves ~the FDR-nominal fraction (not
  the naive uncorrected fraction) of symbols, and the registry artifact records
  the universe-scan trial count.
- Barrier-family determinism test (Section 2/3): an instrument with no session
  boundary in its `calendar_id` cannot select the opening-range/anchored variant
  (it is disabled), and the same code path produces a deterministic
  rolling-Donchian barrier.
- Auto-tune promotion status tests.

## 16. References for implementation choices

These references motivate parts of the design. The code should remain
self-contained and test-driven.

- Adams and MacKay, Bayesian Online Changepoint Detection:
  https://arxiv.org/abs/0710.3742
- Barndorff-Nielsen, Graversen, Jacod, and Shephard, bipower variation:
  https://arxiv.org/abs/math/0503711
- Lee and Mykland jump testing is the intended jump-test family. Use an
  implementation that is validated on synthetic jumps before relying on it.
- Purged/embargoed validation and combinatorial purged CV are required because
  labels depend on future horizons and overlap in time.
- Backtest overfitting controls are required because BLUE search creates
  multiple trials, even when the candidate grid is small.

## 17. Non-goals for this file

These belong to later systems:

- Position sizing.
- Portfolio optimization.
- Multi-signal capital allocation.
- Full execution algorithm.
- Exit strategy after entry.
- Broker connectivity.
- Risk limits across a live book.

This detector must still output the information those later systems need:
entry timestamp, direction, execution urgency, quality score, barrier,
invalidation, stop distance, and evidence decomposition. Per Invariant K, the
quality score is consumed only for BREAKOUT's own gating; downstream composition
branches solely on direction and `status == "entry"`, treating price fields as
levels. The global regime multiplier `g(s_t)` is applied downstream (Invariant
M), not inside this detector.
